## Delivered user workflows

- Job cards open the full job detail and preparation workspace through View & prepare. The separate eye remains available. The employer/source application link remains inside details. Opening a link never marks a successful submission.
- Confirmed career facts now support separate GitHub repository and demo URLs for projects, plus optional LinkedIn, GitHub, LeetCode and Codeforces profiles. Old profiles parse with empty defaults; editing still clears confirmation. PDF and LaTeX exports include these links.
- Each preparation receives an explainable internal résumé compatibility check: 70% recognised JD skill coverage and 30% three text-structure checks. No recognised JD skills yields no numerical score. Required versus preferred skill weighting and actual third-party ATS parsing are not performed. Eligibility remains separate.
- Optional, explicitly requested AI answer drafting uses the existing user-owned connections and quotas. It supplies selected verified fact titles/details, supported questions and bounded JD text, excluding contact fields. Exact quotes, fact IDs, existing numbers and recognised skills are checked. Unsupported drafts and personal declarations are excluded. Accepted drafts show their quotes and require user review; semantic accuracy is not guaranteed by those checks. Resume wording remains the user's confirmed wording, with role-based selection and ordering.
- A user can confirm actual submission, specify an optional known date and role category, correct that metadata with logged history, and select the preparation actually used. The record copies the current JD/résumé/answers and stores a PDF with SHA-256. Stable PDF metadata makes that file byte-identical to the current preparation download. Deleting/editing a preparation does not alter this copy; deleting career data removes submitted profile/document copies. A changed preparation cannot be retroactively claimed as an earlier submitted version. An alternative externally submitted file is recorded as unknown, not invented.
- Application response, OA completion and interview completion are independent milestones with optional scheduled/due dates and revision-protected history. Future scheduled events do not count as completed. The existing stage selector still represents the current outcome; a complete event history for legacy stage changes is not backfilled. These new due dates are recorded only; automatic deadline reminders for them are not implemented.
- My analytics in the sidebar reports current Applied tracker counts, user-recorded milestones, outcomes, role categories and submission months. Unknown dates have their own bucket. CSV, JSON, printable charts and a bounded streamed résumé/history archive are available. Silence is not a rejection. These are observational counts, not causal evidence about résumé quality.

## New discovery category

Jobicy's documented public API is added to the source adapter system alongside the 20 existing ATS employer boards. Its published fair-use guidance permits normal career-product use with attribution: https://github.com/Jobicy/remote-jobs-api and https://jobicy.com/terms-and-conditions (reviewed 18 October 2026).

The API needs no account/key for this access. Canonical Jobicy URLs and attribution are preserved, and actual employer names come from source evidence. The integration uses a fixed endpoint, bounded JSON, redirect refusal and strict row/cursor checks. Jobicy's unspecified Anywhere region is treated as unknown geography, not permission to work worldwide.

Shared ingestion processes at most 100 Jobicy records in one page and persists the opaque continuation in meta. It resumes pages across invocations; it does not buffer the entire rolling window. Source polling leases prevent a new traversal more than hourly, including forced refreshes. Retry-After is respected while resuming too. Page records are idempotent; a crash before checkpointing may repeat an observation, not duplicate a stored job. There is a 20,000-row traversal budget and the retained 20,000-representative catalogue/search budget; raising either needs hosted capacity measurements.

The feed covers a rolling publication window. Disappearance never implies closure. The separate status endpoint distinguishes active, closed and unknown; a status-only check does not refresh the description's evidence age. The current status recheck happens through selected/saved-job checks, not an exhaustive batch re-verification of all historical listings. Records outside the feed become stale for matching until evidence is refreshed. Source counters measure observations and pages; they do not establish complete market coverage or student relevance.

The first bounded live Jobicy page passed with 100 listings and more pages available; none of those first-page rows were classified as internships. Target-cohort usefulness and full live traversal remain unproven. The complete 20-ATS live check passed separately. This is one additional source category, not LinkedIn/Unstop/Internshala ingestion or universal coverage. Licensed search discovery and platform-specific access agreements remain necessary expansion work.

## Nightly job newsletter

Preferences → Alerts & account includes explicit opt-in and a personalised newspaper-style preview. It uses the authenticated account's email; a client-supplied recipient cannot redirect delivery. It sends source-grounded JD excerpts, skills, source/application links and known deadlines for new, fresh, non-uncertain matches. Private imports and already tracked applications are excluded. Publication dates are not fabricated: the window is labelled as discovery time. The email features at most 20 detailed highlights and attaches a CSV containing every matching job with source links, reported skills and deadlines. The complete CSV is bounded at 4 MiB; exceeding that budget pauses the recipient with a visible preparation-failed state instead of sending an unlabelled partial result. The preview can download that same complete list. No LLM call is made for a digest.

The owner-only nextrole_send_daily_digests MCP tool and POST /api/maintenance action email-digests process up to five people per invocation after 21:00 Asia/Kolkata. A real nightly task must be explicitly configured at rollout; existing maintenance schedules are unchanged. Mail is disabled unless all four reviewed environment settings are present: NEXTROLE_MAIL_APPROVAL=approved, NEXTROLE_MAIL_API_KEY, NEXTROLE_MAIL_FROM and NEXTROLE_PUBLIC_URL (HTTPS). No credentials or sender were configured in this work.

The delivery adapter uses Resend's documented /emails API. It includes visible and one-click unsubscribe, an idempotency key, one outbox record per person/day, bounded responses, workspace serialization and a 50-attempt daily pilot budget. Empty digests are not emailed. Provider acceptance is labelled accepted, never inbox-delivered. Preparation failures and ambiguous/rejected attempts pause automatic delivery; interrupted sending states require review. An uncertain message is not automatically retried. The daily cap stops work rather than looping when exhausted. Delivery history has a 30-day cleanup target through existing bounded maintenance; cleanup is delayed if that maintenance is not running. Account deletion removes settings/history; unsubscribe disables further dispatch.

Current provider reference: https://resend.com/pricing lists a free 3,000-email monthly / 100-email daily transactional tier, and a USD 20/month Pro tier. Other account usage, terms and changes can affect availability. No plan was purchased or activated. API/provider reference: https://resend.com/docs/api-reference/emails/send-email. Existing push/in-app alerts remain an alternative; another HTTP email provider can replace this transport. User approval, a verified sender, account checks and actual delivery testing are required before activation. New personal data sent to this transport is limited to the recipient address and personalised public-job email content; inbox access and full career-profile transfer are not used.

## Upgrade, privacy and verification

Append-only migration 0011_application_journey_and_digests adds four tables and indexes. Earlier migrations and the hosting identity are preserved byte-for-byte. No historical submission dates, OA completions or interview events are fabricated during upgrade.

The account JSON export includes application summaries and the streamed history export route; /api/applications?export=1 downloads full submitted documents and raw events in bounded batches with a completion marker. Individual update times identify records; concurrent edits can appear during a long export. This avoids loading all stored PDFs into one Worker response. The new application writes are fenced to their workspace lease, including expiration/deletion races. User ownership applies to every record and document. Career-data deletion also clears cached AI answer drafts. See handoff/VERIFICATION.md for actual checks and remaining rollout gates.
